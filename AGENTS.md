# Workspace Governance

This Codex adapter is separate from the Kimi Code adapter. Codex uses `.codex/`, Codex project instructions/plugins/hooks/skills and Codex project agents; Kimi uses `.kimi-code/` and its native plugin lifecycle, hooks, Skills and AgentSwarm. The Repo Map implementation may be shared, but registration, permissions and runtime evidence are host-specific. Do not infer Codex activation from Kimi evidence or vice versa.

This separation is configuration/integration isolation, not a process sandbox. Codex project agents inherit parent permissions, and the AWG hook only checks selected structured file edits. Shell writes and arbitrary MCP side effects are not fully mediated. Report hook coverage only for observed event delivery and decisions.

The AWG Codex plugin bundles Superpowers v7.0.2. At task start, invoke the exact catalog-listed `using-superpowers` Skill from that bundle, then invoke `awg-workspace-governance` before repository work, project commands, or deployment. Invoke every relevant Superpowers workflow Skill before its stage. If either required Skill is unavailable in the current session, report `BLOCKED: AWG_PLUGIN_UNAVAILABLE` and do not perform repository writes or deployment. If a separately installed Superpowers plugin creates an indistinguishable duplicate Skill entry, report `BLOCKED: AMBIGUOUS_SUPERPOWERS_PROVIDER` and do not claim the AWG-bundled version was used. Record exact invocations in `CAPABILITY`; project configuration or marketplace discovery alone is not proof that the plugin loaded.

## AWG Capability Matrix

- **Skills:** `using-superpowers`, AWG governance, AWG Repo Map, and the bundled Superpowers workflows. Invoke the exact live catalog name before its workflow stage.
- **Repo MCP:** plugin server `awg_repo` exposes `repo_map_status`, `repo_map_get`, `repo_map_refresh`, `repo_docs_search`, `repo_docs_read`, and `repo_context_check`. The current project policy sets `default_tools_approval_mode = "prompt"` and enables these six tools. Pass the project Git root and `.codex/repo-map.json` `workspace_id`; the process rejects a different root before opening its config, then checks the registered workspace, pinned backend fingerprint, and project-local cache before delegation.
- **Project agents:** nine Codex-native agent profiles under `.codex/agents/` inherit the parent session's permissions. They do not create a separate sandbox.
- **Hooks:** `SessionStart` supplies bounded context and binds active task sessions; `PreToolUse` checks only structured `Write`, `Edit`, and `apply_patch` paths against `.codex/awg-task.json`. Hooks do not govern arbitrary shell writes, MCP side effects, or plugin trust.
- **Approval and trust:** plugin enablement, MCP prompt approval, project trust, Skill invocation, MCP connection, hook delivery, and agent dispatch are separate evidence gates. Do not infer one from another.

For an MCP call, first inspect the live connected-server and tool catalog, read `.codex/repo-map.json`, then call `repo_map_status` with `project_root` and `workspace_id`. Use search/read for bounded navigation and read authoritative source for important claims. `repo_map_refresh` remains disabled unless a trusted maintainer explicitly enables it; an approval prompt does not override that workspace policy.

Before changing code, identify the repository root, task scope, entry points, callers, state, authorization and regression surface. Prefer existing components, read source before trusting indexes, and make the smallest change that satisfies the task.

Keep entry points focused on composition; separate domain, storage, network and error handling by responsibility. Validate inputs and handle failures explicitly. Verify in stages: inspect, focused checks, end-to-end path, independent review and acceptance. Record commands and outcomes.

Use the project Repo Map MCP for navigation when configured. It is a bounded index, not source-of-truth or complete impact analysis. Read important source files and run relevant tests. Refresh only when repository policy allows it.

At task start, inspect the complete current session skill catalog and relevant tool/MCP catalogs. Triage every listed skill against the task objective and workflow stages; do not limit discovery to project-owned skills or wait for the user to name one. Invoke every relevant available skill before its related work, and record other skills as `NOT_RELEVANT` with a brief reason. “As needed” means task relevance, not optional discovery or delayed use. Do not invoke unrelated skills merely to use them.

Frontend UI, web page, dashboard, component, or interaction design/implementation/review automatically requires checking and invoking the project `ui-ux-pro-max` Skill before selecting a direction, editing frontend code, or reviewing UI. Use the exact Skill name shown in the live Codex catalog. Use `--design-system` for a new/system-wide direction, a focused `--domain` for UX/style/chart questions, and `--stack` for implementation guidance. Verify that each result's category and product/platform fit the task; retry once with a narrower query and otherwise record no verified match. Treat suggestions as recommendations, never as Owner decisions, and do not persist generated design files or add dependencies without authorization. Also invoke applicable frontend design, modern web, browser, accessibility, testing, and review skills for their stages. This trigger does not depend on the user explicitly asking for a skill.

Before an MCP workflow, inspect the live connected-server and exact-tool catalog. Use relevant MCP capabilities when they materially advance the task; record exact calls and outcomes. If relevant skills or MCP tools are unavailable or fail to invoke, record `NOT_RUN`/`UNAVAILABLE` and the reason. Include a `CAPABILITY` record in task evidence covering the complete skill-catalog triage, invoked skills, relevant MCP decisions/calls, and exceptions. Discovery/configuration is not evidence of invocation or use.

Keep rollout evidence separate by host and stage: projection/static tests, CLI instruction or skill discovery, native plugin activation, active MCP connection/calls, native hook delivery/decisions, project-agent dispatch, and Owner acceptance. Static files, CLI context output, or direct hook unit tests do not prove native Codex Desktop delivery. Preserve `NOT_RUN`, `PARTIAL`, `BLOCKED`, or `DEGRADED` where runtime evidence is missing.

Do not read or write credentials, tokens, session stores or unrelated user-level Codex configuration. Do not commit, push, merge or delete a worktree unless the Owner explicitly authorizes that action. Treat unknown runtime or external state as unknown until directly verified.
