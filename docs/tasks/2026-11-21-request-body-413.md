# CXRG-REQUEST-BODY-413-2026-11-21

Project/repository: Cx-Routing Gateway / AiaiJei/Cx-Routing-Gateway.

Base: `origin/master` at `ba4ad680485fc8001169b88557a42acda3d7246a`. Branch: `codex/request-body-413`. Worktree: `.worktree/request-body-413`.

User report: requests through the local gateway receive HTTP 413 from changing upstream providers, while direct provider access succeeds; a separate running task must remain untouched.

## Current evidence

- `services/gateway/src/server.mjs` used a 1 MiB `MAX_BODY` for every inbound request and rejected before route forwarding.
- A 1.1 MiB same-protocol `/v1/responses` regression against the old code returned HTTP 413 and did not reach the mock upstream.
- The observed client URL is `http://127.0.0.1:15721/v1/responses`, owned at investigation time by `cc-switch.exe`; the repository Gateway default is `127.0.0.1:4318`.
- The changing-upstream symptom is consistent with a Gateway-side limit occurring before provider selection. A 413 returned by a provider after forwarding is a separate provider-side limit.
- The separate running task and its worktree were preserved.

## Implementation

- Replaced the fixed 1 MiB body ceiling with a validated `createGatewayServer({ maxRequestBodyBytes })` option and `CXRG_MAX_REQUEST_BODY_BYTES` environment override; default: 64 MiB.
- A declared oversized `Content-Length` is rejected before buffering. Chunked bodies are bounded while reading, drained without retaining the remainder, and return a readable structured 413.
- Request bytes are retained as buffers and decoded once, preserving UTF-8 characters split across transport chunks.
- Oversized local requests return `{ error: 'request_body_too_large', limitBytes, requestId }`; routing and upstream I/O do not start.
- Documented the local limit and distinguished it from a provider's own 413 response.
