# 上游服务编辑与故障切换稳定性设计

状态：已批准，执行中。日期：2026-11-22。

## 目标

让已创建的上游服务可以在 Desktop 中编辑，并修复并发请求下主上游已经成功却仍被断路器视为不可用、后续请求继续落到备选的问题。用户已选择通过预填弹窗编辑。

## 当前情况与证据

- `UpstreamsPage` 支持新增、测试和删除，没有编辑入口。
- Local Control 已有受鉴权的 `PATCH /v1/control/upstreams/:id`，可更新服务名称、Base URL 和凭证；Desktop IPC、preload、窗口类型和 WorkspaceClient 尚未暴露该操作。
- 凭证不会返回给 renderer。PATCH 只在收到非空 `apiKey` 时替换凭证，因此编辑表单的 Key 应保持空白表示沿用当前凭证。
- 当前 PATCH 先删除旧凭证，再写入新凭证；若新凭证写入失败，旧凭证可能已经丢失。编辑功能需要先安全保存并切换到新引用，成功后再删除旧引用。
- Gateway 按目标顺序选择第一个未熔断的上游。达到路由的失败阈值后，会打开该目标 60 秒；每次请求只记录一个 outcome。
- `recordOutcome` 在识别 outcome 前要求请求代际等于当前代际。阈值触发会提升代际，因此熔断后才完成的同目标成功响应也会被丢弃。
- 用户澄清的现象是优先级 1 正常时仍会突然尝试优先级 2；已复现的并发竞态可造成该行为：多条优先级 1 请求先达到失败阈值，迟到成功被丢弃，后续请求仍被送往备选。截图本身不足以证明该竞态是当时唯一原因。
- 隔离复现：四个请求同时选中优先级 1；其中三个返回 502，第四个在断路器打开后成功；下一请求仍选择优先级 2。现有 Gateway 测试没有故障切换回归覆盖。
- 用户截图显示优先级 1 的三条失败日志之后才由 `apikey` 处理；这组日志符合三次失败的切换阈值，截图没有显示同期有优先级 1 的成功响应。页面的“已连接”由 `lastCheckedAt` 推导，表示曾完成过检测，不代表当前请求实时健康。因此并发迟到成功竞态已在代码中复现，但尚不能断言它是截图中那一轮的唯一原因。
- 基线：Gateway 测试 34/34 通过；Desktop `UpstreamsPage` 测试 6/6 通过。

## 方案比较

1. **按完成顺序更新所有结果。** 实现简单，但阈值触发后的旧失败仍可能再次计数并重新打开断路器。
2. **按请求发起顺序重排结果。** 可建立严格的连续结果顺序，但需要额外队列和等待处理，并发情况下引入更多状态。
3. **保留失败代际隔离，接受成功恢复信号（建议）。** 旧代际失败不再改变当前状态；同一目标的成功响应无论所属代际都清除失败计数和熔断时间，并提升代际以屏蔽更早发起但更晚返回的失败。只要已有成功结果表明该目标可用，后续请求就恢复优先级顺序。

编辑功能沿用现有 PATCH 控制 API 和 Desktop IPC 边界，不另建更新 API；使用已选定的预填弹窗。该方案减少重复的凭证验证、DNS 校验和安全策略代码。

## 预期行为

### 编辑上游

- 每条运行时上游提供“编辑”操作，打开“编辑上游”弹窗。
- 服务名称和 Base URL 从当前记录预填；API Key 输入框不预填任何值，留空保留原凭证，输入新值则替换原凭证。
- 替换凭证时先把新密钥写入密钥库并持久化新引用；只有更新成功后才删除旧引用。失败时保留旧引用，且不在 renderer 中暴露密钥。
- 修改 Base URL 时，如果请求没有显式传入 `allowPrivateNetwork`，沿用当前上游的 `trustedPrivateNetwork` 设置进行目的地址校验和保存；显式值仍按用户输入更新。
- 保存经 Desktop IPC 调用现有 PATCH 端点并继续使用控制令牌鉴权；成功后刷新 Workspace 数据并显示状态，失败时保留弹窗和输入内容并显示错误。
- 示例/fixture 模式沿用当前页面会话内的编辑语义，不声称持久化或连接网络。
- 不向 renderer 暴露凭证明文，也不扩大可编辑字段到路由的出站协议配置。

### 故障切换

- 仅达到已配置失败阈值的目标错误继续打开断路器；阈值、状态类别、60 秒冷却和“不重试当前失败请求”的既有策略不变。
- 同一目标的成功响应清除连续失败计数并关闭其当前熔断；通过递增代际使旧请求的迟到失败不再影响已恢复状态。
- Gateway 的健康签名包含影响目标可达性和路由行为的上游配置（如 Base URL、协议、凭证引用、启用状态及目的地址信任信息），避免编辑后的主上游继续继承旧熔断状态。展示名称和模型发现结果不参与签名。
- 上游状态仍按路由和目标隔离；某个备选目标的结果不能清除另一个目标的断路器。

## 范围

包含：编辑弹窗、IPC/PATCH 接线、受控表单状态、凭证替换失败保护、Gateway 断路器恢复处理、路由相关上游配置变化时的健康状态刷新、对应回归测试和专属 PR。

不包含：修改失败阈值或冷却时间默认值、改变可配置的 4xx/5xx 类别、增加手动重置或探活机制、重试已失败请求、真实第三方调用、发布或合并 PR。

## 约束与验收

- 不增加运行时依赖；遵循现有 React/Electron、Modal、WorkspaceClient、Local Control 和 Node test 模式。
- 运行时更新须通过现有控制令牌路径；API Key 仅在 IPC 调用和本地密钥库之间传递。
- 自动化验收覆盖：编辑时名称/Base URL 预填、空 Key 保留凭证、新 Key 写入失败时旧凭证仍可用、成功刷新、失败保留输入、fixture 语义；三个主上游失败后进入备选；少于阈值后成功会清零；阈值触发后同一主上游迟到成功恢复优先级；编辑影响路由的上游配置后不继承旧熔断。
- 完成 Gateway 和 Desktop 测试、Desktop TypeScript/Vite 构建、`git diff --check`，检查改动范围；提交分支并创建一个面向 `master` 的专属 PR。
- worktree 使用 `.worktree/upstream-service-edit`，分支使用 `codex/upstream-service-edit`；创建前再次确认两者均不存在，若冲突则停止且不覆盖。

## 执行修订

- 用户选择预填弹窗并回复“执行”，批准按本设计实施。
- 用户指出原先对故障现象的描述有出入：问题是优先级 1 正常时也会突然尝试优先级 2。保持现有三次失败阈值不变；通过迟到成功恢复目标健康状态，修正并发结果被错误忽略的竞态。
- 实施计划补充私网信任保留规则：编辑 Base URL 时省略该字段应继承现有信任状态，避免把合法的私网目标误判为未授权。
