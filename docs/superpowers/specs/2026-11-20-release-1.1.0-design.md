# Cx-Routing Gateway 1.1.0 Release Design

## Intent

Prepare a formal 1.1.0 desktop release based on merged PR #9. Replace the generic Windows application icon, connect Settings update checks to this private repository's GitHub Releases, publish a single-file Windows x64 portable executable to GitHub and the user's Desktop, and retain the existing user-initiated NSIS installation path.

## Goals

- Set the desktop application and release artifact version to `1.1.0`.
- Use one product icon for the Electron window and Windows build outputs.
- Keep `AiaiJei/Cx-Routing-Gateway` private. Let each authorized app user configure a fine-grained GitHub token limited to repository `Contents: Read`, then use it to read release metadata and download assets.
- Store the token encrypted with Electron `safeStorage` in the app's user-data directory. Accept it from the UI only as a password-field value passed over trusted IPC into main; never return it to the renderer or include it in logs, status responses, URLs, or release artifacts. If OS-backed encryption is unavailable, refuse to save/use the token rather than falling back to plaintext.
- Check the latest stable release and compare its `vX.Y.Z` tag with the installed version. Require GitHub's asset SHA-256 digest for the expected NSIS installer and verify downloaded bytes before launching it.
- Add Settings controls to configure/replace, verify `Contents: Read` access, and remove the stored update token; show whether credentials are configured without revealing their value.
- Build a single Windows x64 electron-builder `portable` `.exe` that the user can double-click without installing or manually extracting a ZIP; place a verified copy on the user's Desktop.
- Prepare concise, formal Chinese GitHub release notes and create a dedicated PR #10 based on merged PR #9.

## Non-goals and constraints

- No repository visibility change, public update proxy, embedded/shared maintainer token, automatic background install, backend/protocol/data migration, installerless in-app self-replacement, or 32-bit portable package.
- Keep GitHub requests and credential storage in Electron's main process behind the current trusted IPC boundary. Renderer code receives only credential status, update status, version and release URL.
- Keep the existing NSIS installer as the explicit update action; the portable executable is a separate, no-install download.
- Do not commit Desktop build outputs or generated release files into the repository.
- The user authorized branch work, commits/pushes needed for PR #10, and publishing the requested GitHub Release. The repository instructions distinguish PR creation from merging. Release publication will target the PR #10 changes after they land on the release branch; merge itself remains a separate owner decision unless explicitly authorized.
- Preserve all pre-existing untracked paths and worktrees. Use the existing task worktree `.worktree/release-1.1.0` and branch `codex/release-1.1.0`.

## Approaches

1. **Per-user fine-grained token (selected).** Keep the source private and let each authorized user supply a repository-scoped token with only `Contents: Read`. Store it with OS-backed `safeStorage` and use it only in main-process GitHub requests. This fits the repository's current privacy and avoids sharing a maintainer credential; it adds one-time setup for each app user.
2. **Make the repository public.** This removes credential setup and enables anonymous release checks, but exposes the repository contents and history. The owner chose to keep the repository private.
3. **Public update proxy.** This keeps the app token-free while a hosted service reads private GitHub releases. It requires a separate service, secret management and ongoing hosting/availability work not present in the repository.

## Behavior and implementation choices

- The Electron main process owns an encrypted token store. Save/replace, status and remove operations are exposed through trusted preload IPC; no renderer network request or token readback is allowed.
- Before storing a token, verify it with authenticated `GET /repos/{owner}/{repo}/contents`; this works before a Release exists and proves the required content-read permission. Update checks and installation load the token in main-process memory and send it as an Authorization header to the fixed repository's GitHub API and GitHub asset URL. Do not persist the token in environment variables, source, logs, browser storage, updater metadata or returned IPC data.
- The app reports a clear setup-needed state when no token is configured; it reports access/network/schema failures without exposing the token. Drafts and prereleases are rejected, and a stable release is considered available only when its expected version-matched NSIS installer has a valid `sha256:` digest.
- Installer download verifies SHA-256 before writing the file or launching it. The user still explicitly starts installation from Settings.
- Produce a Windows x64 single-file portable executable with electron-builder's `portable` target; retain required runtime resources. Use a product-specific multi-resolution ICO for Windows packaging and the app window.
- Validate the portable executable's AMD64 PE architecture and launch it directly before copying it to the Desktop. Keep the release notes and asset checksums as release evidence.

## Evidence and acceptance

- Token-store tests prove encrypted-at-rest storage, no plaintext fallback when `safeStorage` is unavailable, replacement/removal, and no token readback.
- Local HTTP fixture tests prove the configured token is sent only as an Authorization header to the fixed API/asset hosts; cover missing/invalid token, stable/prerelease/draft handling, version comparison, missing digest, tampered download, and GitHub errors.
- Desktop and Runtime test suites pass; TypeScript/Vite production build passes.
- Windows x64 packaged app launches, required runtime resources are present, and the portable `.exe` starts directly without installation or manual extraction.
- The portable executable and NSIS installer hashes match recorded release digests. With an authorized read-only token and a published stable `v1.1.0` release, the Settings updater recognizes and links to that release.
- PR #10 is based on the merged PR #9 commit and has passing required CI. GitHub Release contents and Desktop copy are inspected after creation.

## Rollback

Before publishing, revert only task commits through a follow-up commit if needed; preserve generated local artifacts and the user's stored runtime data. A token is removable from Settings and is stored separately from app preferences. After publishing, mark the GitHub Release as a draft or remove its tag only with explicit owner authorization.

## Roles and remaining decisions

- Implementer: inspect and modify updater, main-process credential storage/IPC, Settings token controls, icon, packaging, version metadata, tests and task evidence in the isolated task worktree.
- Owner: review/merge PR #10 and approve any release/tag rollback.
- No new dependency is planned unless existing APIs cannot implement encrypted storage or generate a multi-resolution ICO/ZIP.
